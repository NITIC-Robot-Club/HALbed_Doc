# 電源再投入時に起動しないマイコン

## はじめに

既製品の基板でファームウェアを変更していたとき、電源を短時間だけ切って再投入するとマイコンが起動しない、という現象に遭遇しました。

電源を切って数秒待てば正常に起動します。ところが、電源を切ってすぐに入れ直すと、ステータスLEDが実装されていないパターンで点灯します。

最初は、電源電圧が十分に下がっていないことが原因だと考えました。しかし、3.3 Vが0 Vまで下がったことを確認してから再投入しても、起動に失敗します。VDD、VDDA、VBAT、NRSTも確認しましたが、テスターで見る限り大きな異常はありませんでした。

使用している環境はCubeIDEではなく、デバッグモードも使えません。そこで、マイコンがどこまで動いているのかを、SWD経由で調べることにしました。

## SWDでSTM32の状態を確認する

まず、ST-Linkを接続し、OpenOCDからSTM32G4へ接続します。

```bash
openocd \
  -f interface/stlink.cfg \
  -f target/stm32g4x.cfg
```

異常な状態でも、OpenOCDはSTM32を認識できました。

```text
Info : Target voltage: 3.150195
Info : [stm32g4x.cpu] Cortex-M4 r0p1 processor detected
Info : [stm32g4x.cpu] target has 6 breakpoints, 4 watchpoints
```

この時点で、STM32自体が完全に停止しているわけではないと分かります。CPUには電源が入り、SWDからアクセスもできています。

では、CPUはどのプログラムを実行しているのでしょうか。

## Program Counterを確認する

OpenOCDを起動したまま、別のターミナルから接続します。

```bash
telnet localhost 4444
```

CPUを停止させます。

```text
halt
```

このとき、次のような表示が出ました。

```text
[stm32g4x.cpu] halted due to debug-request, current mode: Thread
xPSR: 0x41000000
pc: 0x1fff3b5e
msp: 0x20002140
```

ここで見るべきなのが、`pc`、つまり **Program Counter（プログラムカウンタ）** です。PCは、CPUが現在実行している命令のアドレスを示します。

STM32の通常のユーザープログラムはFlash上にあり、一般に次のアドレス付近から実行されます。

```text
0x08000000～
```

ところが、異常起動時のPCは次の値でした。

```text
PC = 0x1FFF3B5E
```

`0x1FFFxxxx`はユーザーFlashの領域ではありません。STM32内部の **System Memory** と呼ばれる領域で、STがあらかじめ書き込んでいるROMブートローダが格納されています。

つまり、STM32は起動に失敗して停止していたのではありません。対象のプログラムではなく、STM32内蔵のブートローダを実行していました。

ここで、調べるべき対象が変わります。電源そのものではなく、なぜ起動先がSystem Memoryに変わったのかを確認する必要があります。

## Flashが壊れていないか確認する

念のため、ファームウェアが書き込まれているFlashも確認しました。

OpenOCDから次を実行します。

```text
mdw 0x08000000 4
```

結果は次のとおりでした。

```text
0x08000000: 20018000 08056219 0805627d 0802af71
```

先頭の`0x20018000`は、初期スタックポインタとして妥当なRAMアドレスです。その次の`0x08056219`もFlash内のアドレスになっています。

Flash上には、正常なファームウェアが存在していました。プログラムが消えたり壊れたりしたのではなく、そこから起動していなかったわけです。

## STM32はどこから起動するのか

STM32はリセット直後に、次のような領域から起動できます。

- Main Flash
- System Memory
- SRAM

起動元を決める信号が`BOOT0`です。STM32G474では、`PB8`ピンが`BOOT0`の機能も持っています。今回使用している基板では、このPB8を通常の信号としても使用しています。

ここで問題になるのが、STM32の **Option Bytes** です。

## Option Bytesを確認する

Option Bytesは、STM32の起動方法やFlash保護などを設定する特殊な領域です。
OpenOCDから`FLASH_OPTR`を読み出しました。

```text
mdw 0x40022020 1
```

結果は次のとおりです。

```text
0x40022020: ffeff8aa
```

つまり、

```text
FLASH_OPTR = 0xFFEFF8AA
```

です。

ブートに関係する設定を確認すると、次の値になっていました。

```text
nBOOT0   = 1
nSWBOOT0 = 1
nBOOT1   = 1
```

今回のポイントは`nSWBOOT0 = 1`です。この設定では、起動時に物理的な`BOOT0`ピンの状態を見て起動先を判断します。

```text
BOOT0 = Low
    ↓
Main Flash
    ↓
ファームウェア
```

```text
BOOT0 = High
    ↓
System Memory
    ↓
STM32内蔵ROMブートローダ
```

異常起動時のPCが`0x1FFF3B5E`だったことを考えると、電源投入時に`BOOT0`がHighとして判定された可能性が高いと考えられます。

## なぜテスターではBOOT0の異常が分からなかったのか

BOOT0をテスターで測定すると、起動後には特に異常が見つかりませんでした。これは、BOOT0が重要になるのが起動直後の一瞬だけだからです。

電源投入直後に`BOOT0 = High`と判定されれば、その後にBOOT0がLowへ戻っても起動先は変わりません。CPUはそのままSystem Memoryのブートローダを実行します。

テスターでは、このような短時間の変化を確認できません。「起動後に0 Vだから問題ない」とは判断できないわけです。今回はオシロスコープを使えなかったため、PCの値を確認することで、実際にSystem Memoryへ入っていることを突き止めました。

回路を確認すると、BOOT0は浮いた状態でした。そのため、電源投入時にHighとして読み取られる可能性は十分にあります。

## 対策

本来は、BOOT0をプルダウンしておくのが確実な対策です。しかし、実装できない場所だったので、今回は、Option Bytesを変更してソフトウェア側で対応しました。

STM32CubeProgrammerのOption Bytesで、次のように設定します。

```text
nSWBOOT0 = 0
nBOOT0   = 1
nBOOT1   = 1
```

CubeProgrammer上では、次の状態にします。

```text
nSWBOOT0 : チェックなし
nBOOT0   : チェックあり
```

`nSWBOOT0 = 0`にすると、物理的なBOOT0ピンの状態を起動判定に使わなくなります。代わりに、Option Bytesの`nBOOT0`が使われます。`nBOOT0 = 1`としているため、Main Flashから起動します。

```text
PB8 / BOOT0の電圧
        ↓
      無視
        ↓
Option BytesでMain Flashを指定
        ↓
ファームウェア起動
```

Option Bytesを変更したあと、これまで失敗していた短時間の電源OFF→ONを繰り返しましたが、正常に動作しています。

## 原因の整理

今回の問題は、電源電圧そのものが不足していたわけではありません。異常起動時もSTM32は動作していました。ただし、実行していたプログラムが違っていました。

```text
短時間の電源OFF
        ↓
電源再投入
        ↓
BOOT0がHighとして読み取られる
        ↓
nSWBOOT0 = 1なのでBOOT0ピンを参照
        ↓
System Memoryから起動
        ↓
PC = 0x1FFFxxxx
        ↓
ファームウェアが実行されない
```

対策として、Option Bytesを次のように設定し、Main Flashからの起動に固定しました。

```text
nSWBOOT0 = 0
nBOOT0   = 1
nBOOT1   = 1
```

## Option Bytes変更による影響

この設定にしても、次の機能には基本的に影響しません。

- ST-Link / SWDからの書き込み
- 通常のファームウェア
- ブートローダを使用した更新
- PB8のGPIOとしての使用

一方で、**BOOT0ピンをHighにしてSTM32内蔵のSystem Memory Bootloaderへ入る方法** は使えなくなります。

通常の運用では、SWDまたは基板側のブートローダを使用できます。今回の構成では、この制限が大きな問題になることはありません。

## Option Bytesは毎回設定する必要があるか

Option Bytesは、通常のプログラムFlashとは別に保存されます。そのため、一度次のように設定すれば、電源を切っても設定は保持されます。

```text
nSWBOOT0 = 0
nBOOT0   = 1
nBOOT1   = 1
```

通常のファームウェア更新で、Option Bytesが変更されることも基本的にはありません。

新しい基板へ最初にプログラムを書き込むときに、次の工程まで実施すれば十分です。

```text
ファームウェア書き込み
        ↓
Option Bytes設定
        ↓
書き込み確認
        ↓
電源再投入試験
```

基板を複数製作する場合は、初期書き込み用のスクリプトにOption Bytesの設定も組み込んでおくと、設定忘れを防げます。

## SWDデバッグで覚えておきたいこと

今回の調査では、最初は「マイコンが起動していない」と考えていました。
しかし、SWDから確認すると、CPUは動作していました。こうした場合は、次のコマンドでPCを確認するだけでも大きな手掛かりになります。

```text
halt
reg pc
```

たとえば、

```text
PC = 0x080xxxxx
```

なら、基本的にはユーザーFlash上のプログラムを実行しています。

一方、今回のように、
```text
PC = 0x1FFFxxxx
```
となっていれば、System Memoryなど別の領域を実行しています。
「動いているか」だけでなく、「どこを実行しているか」を確認すると、電源問題に見えた現象を、ブート設定の問題として切り分けられます。

ロボ部の基板では、回路でbootボタンついていたり対策されているはずなので必要になることは少ないと思いますが、既製品のファームウェアをいじる時などに参考にしてください。
