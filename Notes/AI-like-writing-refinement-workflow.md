# AIらしさを抑える文章修正ワークフロー

## 目的

技術文書を、生成AIが一律に整えたような文章へ変えてしまわず、自然な人間の文章を残したまま読みやすくする。

参照した記事：

- [生成AI以前と以後でエンジニアの文章はどう変わったのか](https://nyosegawa.com/posts/qiita-writing-before-after-ai/)

記事から得た要点は、AIらしさは単語一つではなく、太字・箇条書きの多用、抽象語の連続、均一な文のリズム、定型的な結論表現の組み合わせに現れるということ。よく挙げられる「しましょう」などの語が必ずAIらしいとは限らないため、単語の一括置換は行わない。

## 対象範囲の決め方

- 技術記事、導入説明、FAQなど、読者向けの本文Markdownを対象にする。
- API仕様書、生成ページ、タグページ、UI設定、コード・設定ファイルは原則として対象外にする。
- 技術的に正確な語（例：実装入口、既定値）や、書き手の経験・判断が自然に表れている文は残す。
- 文章が自然なら修正しない。変更数を増やすことを成果にしない。

## 修正の判断基準

### 修正する

- 同じ内容を言い換えて繰り返している。
- 「本記事では」「ここでは」「次に説明します」など、本文の進行だけを説明している。
- 「重要です」「要点です」「〜とは別物です」などの評価表現が連続し、具体的な条件や結果がない。
- 「土台」「入口」「核心」などの比喩で、対象の関係がかえって曖昧になっている。
- 一文に条件・理由・結論を詰め込みすぎている。
- 明らかな誤記、重複、助詞の誤りがある。

### 残す

- 技術用語として意味が固定されている表現。
- 数値、条件、例外、実測結果、コードとの対応を説明する文。
- 書き手の経験や判断が読み手の理解に役立つ文。
- 初学者向けの親しみやすさや、文書固有の語り口。
- まとめ、箇条書き、太字が情報の構造を明確にしている場合。

## 編集時の不変条件

- YAML frontmatter、数値、技術用語、リンク、画像、表、コードブロックを維持する。
- APIの仕様やサンプルコードを書き換えない。
- 事実を補うために、根拠のない説明や一般論を追加しない。
- 文章全体を同じ調子に均質化しない。

## 実施手順

1. 現在のブランチと作業ツリーを確認し、既存の変更を保護する。
2. 必要なら `dev` を起点に専用worktreeと `fix/...` ブランチを作る。
3. Semble検索または候補語の全件検索で、定型句・重複・抽象表現の候補を抽出する。
4. 候補を前後の段落と一緒に読み、自然な文は除外する。
5. 具体的な事実・操作・結果が分かる形へ、必要最小限だけ修正する。
6. 差分で対象外ファイル、frontmatter、コードブロック、リンクに変更がないことを確認する。
7. `npm run docs:build` と `git diff --check` を実行する。
8. 生成ファイルは、内容差分が必要な場合だけ変更対象に含める。

## 環境上の注意

- Windowsのworktreeでは、Sembleのdocs検索がインデックス処理や権限解決で長時間停止することがある。その場合は検索を停止し、`rg`で明示的な候補語を全件検索して本文を直接確認する。
- VitePressのビルドがworktreeのGit管理パス解決でAccess deniedになる場合がある。通常実行で再試行し、必要なら権限付きで同じビルドを再実行する。
- `npm run docs:build` 後に生成catalogがGitのstat上だけ変更扱いになることがある。`git diff --quiet -- .vitepress/theme/generated/contentCatalog.ts` で内容差分を確認する。
